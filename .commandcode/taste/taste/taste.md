# Taste
- When asking "how does X work?" questions, wants answers that pair a general/conceptual explanation of how it typically works in such applications with a concrete walkthrough of what the current codebase actually does, plus an honest verdict on quality/robustness — not just a description. Confidence: 0.6
- When security/robustness gaps are identified, wants them fixed comprehensively to production-grade ("make this robust and completely strong") — full multi-file hardening (fail-fast production configs, secret rotation, removing insecure scripts/scripts-allowing bypasses), not minimal or partial patches. Confidence: 0.8
- When resolving merge conflicts, security hardening takes precedence: re-apply protections the incoming upstream commits lack (e.g. re-adding `JwtAuthGuard`/`RolesGuard` on admin routes), while adopting upstream's more-evolved feature versions over stale local WIP duplicates of the same work. Confidence: 0.7
- Windows dev environment: default shell is cmd — no Unix tools (awk/head/tail); use PowerShell for text processing/filtering and cmd builtins (`findstr`, `type`, `copy /y`) otherwise; one-off DB/env tasks go through scratchpad `.cjs` scripts run with node + `NODE_PATH`. Confidence: 0.7
- Match script file extension to the module system actually used in that directory: root `scripts/` is CJS (`.cjs`, `require`/`dotenv`) even in a TS/ESM repo — don't write a `.ts` file there expecting transpiled execution. Confidence: 0.8
- Place a script in the workspace that owns its dependencies: in this pnpm monorepo, deps like `dotenv` and `@aws-sdk/client-s3` only resolve inside `apps/api/node_modules`, so such scripts belong in `apps/api/scripts/` and are run from there; a root-level script fails to resolve them and needs fragile path hacks. Load the root `.env` with `path.resolve(__dirname, '../../../.env')`. Confidence: 0.7
- MCP servers are registered project-scoped via `cmdc mcp add --scope project <name> -- <command>`, pointing at wrapper scripts under `scripts/mcp/` that load `.env` before spawning the server — registering the raw `npx` command from docs drops the env vars the server needs. Confidence: 0.7
- Before generating a new Drizzle migration, check for pre-existing uncommitted migration files — an in-progress migration may already contain the column, and generating on top of a diverged snapshot produces a stale migration that recreates existing tables. Confidence: 0.8
- Safe pull with a dirty tree: check status/branches/remotes and fetch to review incoming commits before touching anything, check overlap between dirty files and incoming changes, `git stash push -u` (include untracked) before pulling, `git pull --ff-only`, then pop and resolve conflicts file-by-file; verify no conflict markers remain, stage resolved files, drop the stash, and rebuild + typecheck everything before calling the merge done. Confidence: 0.6
- On migration-number collisions with upstream, renumber own migration on top of upstream's rather than deleting theirs, and reconcile live-DB schema drift with idempotent `ADD COLUMN IF NOT EXISTS` verified via information_schema. Confidence: 0.6
- Flag it when the user's own prior work interacts badly with a new finding (e.g. the public-read S3 bucket policy they just approved escalates an unvalidated-`s3Key` ownership bug), and re-check whether a just-landed infra change reopened or worsened an existing issue. Confidence: 0.7
- NestJS features must follow a strict 3-layer pattern: Controller (HTTP/API) → Service (business logic) → Repository (Drizzle) → PostgreSQL, with the module wiring the components together and DTOs/Zod schemas defining and validating the data contracts. Services must not query Drizzle directly; a Repository owns each table/aggregate's queries so shared access logic (e.g. "primary photo for profile(s)") lives in one place instead of being copy-pasted across modules. Confidence: 0.9
- Privacy must be enforced server-side by withholding data, not hidden client-side: when a photo should be blurred the API returns no S3 key at all and the frontend renders a locked placeholder — chosen over both CSS-only blur and serving blurred photos via signed URLs, because the media bucket is publicly readable so a key sent to the browser is viewable regardless of any blur flag. Confidence: 0.75
- New gating/filters must not make existing content disappear: backfill existing rows to the permitted state first (11 pending photos → approved, verified per-profile that nothing was orphaned) and let new uploads stay visible immediately while being flagged for review, rather than hiding everything until a moderator approves it. Confidence: 0.7
