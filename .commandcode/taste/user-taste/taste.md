# User taste
- Prefers explanations that contrast how something is *typically* done vs. what their codebase *actually* does, with an honest verdict on quality ("tell me how a typical authentication setup works ... and what our application is doing"; the direct "Honestly — no" assessment landed well). Confidence: 0.7
- Gives short, high-level directives ("yes lets go ahead", "lets pull main and dev locally") and expects the agent to plan autonomously (todo lists), execute end-to-end, handle obstacles, and summarize what changed plus any remaining action items; when the same directive comes back after a plan was already approved, resume the in-flight implementation rather than re-planning. Confidence: 0.8
- Wants comprehensive fixes, not minimal patches: after a review surfaced many security gaps, asked to make the system "robust and completely strong" — expects every identified finding addressed systematically, then verified. Confidence: 0.8
- Prefers live verification over static checks: explicitly asks to test integrations immediately ("tell me if we can do this and lets test it now"); smoke-test with a running server and curl in addition to build/typecheck. Verify negative cases too — after making something public, prove what must stay private still rejects (credential-free/anonymous fetch, private bucket 403, non-public prefix 403) and that content types survive metadata rewrites. Confidence: 0.85
- Wants research done before implementing unfamiliar performance/infra work: asks to "search the web properly" on how the industry solves it, understand current approaches, then implement the same thing — don't jump straight to a hand-rolled design. Confidence: 0.8
- Prefers unblocking blocked infrastructure by shipping a simpler working path now with a clean seam to upgrade later (e.g. serve images from public S3 directly, leave a single env var, `NEXT_PUBLIC_CLOUDFRONT_URL`, to swap in CloudFront with zero call-site changes) rather than waiting on the verification. Confidence: 0.8
- Expects any manual out-of-band step to be handed over as runnable instructions, not left implicit: exact AWS console steps plus a checked-in policy/config file and a copy-pasteable CLI command, and idempotent `--dry-run`-first backfill scripts for existing data. Confidence: 0.8
- Expects validation to prove no regression rather than just "it builds": compare lint/typecheck counts against a pre-change baseline (e.g. `git stash push` → lint → `stash pop`) to show errors were reduced and none introduced. Confidence: 0.7
- Develops on Windows (cmd shell): use `type`/`del`/`findstr`/PowerShell instead of `cat`/`rm`/`awk`; bracketed paths like `apps/web/src/app/profiles/[profileId]/page.tsx` break `read_file` (returns empty), but `edit_file` and `grep` accept the literal path — edit in place with exact-match strings rather than temp-copying just to read. Confidence: 0.9
- The Command Code CLI must be invoked as `cmdc` in this environment — bare `cmd` resolves to Windows `cmd.exe` and just prints a shell banner. `cmd`, `cmdc`, `command-code`, and `commandcode` are all the same entrypoint, so `cmdc` is the safe name. Confidence: 0.75
- When an out-of-band infra step is handed over (e.g. "apply this S3 bucket policy in the console", or "use the aws mcp to clone and then add the env and do the changes and then lets also fix the vercel as well and its env"), the user wants the agent to just perform it instead of handing back runnable instructions. They asked for the AWS MCP specifically so S3/EC2-side changes could be made directly. Execute the change when credentials and tooling are present, and still keep the runnable handoff docs accurate for the parts that genuinely require human clicks. Confidence: 0.75
- Adds agent tooling by pasting raw `mcpServers` JSON config blocks with a bare "set these up" — expects them translated into registered, working MCP servers; the standing toolkit is the remote `aws-mcp` (us-east-1, OAuth-initialized) plus npx-spawned `@playwright/mcp` and `chrome-devtools-mcp` for browser automation. Confidence: 0.7
- Stale env vars (`NODE_ENV=production`, `MOCK_OTP_ENABLED=true`, `JWT_SECRET`, `JWT_EXPIRES_IN`) shadow the repo `.env` (dotenv never overrides existing vars) — but they are session-scoped, NOT system-wide: User/Machine env scope, HKCU/HKLM registry, and PowerShell profiles are all clean; they were typed into the PowerShell (Windows Terminal) window that launched the session, so child processes inherit them. When `.env` behavior doesn't win, check with `set VAR`, launch with explicit `set VAR=...&&` overrides, and trace the source before deleting (env scope → registry → `$PROFILE` files → parent process chain); a fresh terminal is clean and `.env` is authoritative. Confidence: 0.9
- Prefers the repo `.env` as the single source of truth for project configuration: immediately approved deleting the shadowing env vars when offered with a reversibility note ("alright lets delete those") — no duplicate config kept in system/session env. Confidence: 0.8
- Main project: pnpm monorepo (NestJS API + Next.js web with an httpOnly-cookie BFF proxy; shared packages for schema/validation/types using Drizzle + PostgreSQL), deployed on EC2 (API) and Vercel (web); uses `main` + `dev` branches on origin. Confidence: 0.8
- When asking to review a feature, wants the whole connected path traced end-to-end (e.g. S3 object storage → API endpoints → DB tables) and audited against the project's documented architecture, tech stack and design — with deviations, duplicated logic, and any security/data-integrity bugs found along the way called out explicitly, plus a suggested order of fixes. Verify agents'/subagents' high-severity claims directly before reporting them; they accepted the habit of spot-checking with grep before publishing an audit. Confidence: 0.85
- Separately asks for a plain-prose inventory of the features that currently exist ("tell me the features that are there in words"), each with the issues found in it — not just a raw issue list. Include dead code (schema columns written but never read), hardcoded/fake values (e.g. `photoVerified: true`, fabricated matchPercent), and features that appear implemented but aren't enforced; close with a prioritized "which would you start with" choice. Confidence: 0.7
- Easy to mislead with confident corrections: the user accepts it immediately and explicitly when the agent admits a wrong call ("I owe you a correction..."). Correct the record proactively when new evidence arrives, and also flag when own earlier work made a finding worse (e.g. a public-read bucket policy escalating an s3Key ownership bug). Confidence: 0.75
- Works with parallel agent sessions/GUI tools against the same repo and syncs context by pasting raw command+output blocks (including other sessions' summaries like "Recovered and restored...") into chat; the working tree can change mid-conversation, so re-verify git status/stash/remotes before editing instead of trusting in-session assumptions. Confidence: 0.6
- When a review's findings are offered as a prioritized choice, they pick by user-visible trust impact first: chose "trust-visible" fixes (real verification badges, real moderation status, enforced photo privacy) over latent security bugs (reorder IDOR, unvalidated s3Key ownership). On this matrimonial product a "Verified" badge that means nothing is treated as worse than a hidden security bug. Confidence: 0.7
- Answer blocking decision-questions readily: asking up front with concrete options plus a recommended default — framed as "this will break the app if I guess wrong" — got both answers immediately and unblocked the work. Use this only for genuinely destructive or irreversible calls; routine work should still be planned and executed autonomously. Confidence: 0.65
- Wants a confirmation checkpoint before writing to the shared production RDS database, and approves quickly when the ask states the row count, idempotency and reversibility ("11 pending → approved", "safe to re-run"). Confidence: 0.6
- When auditing a cross-cutting concern (e.g. auth/authz) across the whole app, scopes it surface-by-surface in deliberate phases ("first lets do it for the users"), expecting a comprehensive per-surface audit before moving to the next surface — not a shallow sweep of everything at once. Confidence: 0.6
- For cross-cutting app-wide hardening on this matrimonial product, defaults to requiring JWT on catalog/lookup reads (plans, locations, educations, careers, communities) rather than leaving them public — chose stricter policy explicitly when offered the public/JWT choice. Treat reference data as confidential-by-default for this product. Confidence: 0.65
- When offered a scope choice for a big cross-cutting ask (security-only vs security+perf vs security+perf+ops), picks the middle option: concrete user-visible speedup (N+1 fixes, query batching, indexes) without committing to full observability/Redis/Sentry work. Prefers real measurable wins over infra completeness. Confidence: 0.65
- Scope-aware commit hygiene: when the working tree mixes own-session work with files from other parallel sessions/agents (`.commandcode/`, `.mcp.json`, `taste.md`, EC2 scripts, S3 docs, deploy workflows, migrations), the commit must contain only what was authored this session — selectively `git reset HEAD -- <paths>` to unstage the non-owned additions rather than committing everything with `git add .`. Always re-list `git status --short | findstr "^A "` after staging to confirm only own additions remain before committing. Confidence: 0.85
- After a hardening pass, run the FULL test suite (not just files touched this session) and transparently report the breakdown — owned tests vs pre-existing drift/failures in untouched files — rather than hiding or claiming a green run. Proves the diff is innocent by listing exactly which test files were modified and showing they're all in the PASS column. Confidence: 0.8
- Prefers detailed multi-section commit messages for big hardening passes (Section A / Section B / Section C … structure) that document both what changed and the verification evidence at the bottom ("Verified: build, typecheck, smoke checks …") so the commit itself is reviewable without re-running anything. On Windows cmd, heredoc-style `git commit -F - <<EOF` gets swallowed by quoting; write the message to a temp file (`write_file` → `C:\Users\...\Temp\commitmsg.txt`) and pass it via `git commit -F "<path>"`. Confidence: 0.8
- Wants a specific pre-push verification gate before any code is committed and pushed: (1) check `git status` to see what's committed vs uncommitted, (2) verify which files are already pushed to `origin/main` vs local-only (e.g. `git merge-base --is-ancestor`), (3) typecheck, (4) build, (5) only then commit + push. Both typecheck AND build must pass — not just one — and the user treats the build result as a hard gate. Confidence: 0.65
- After committing/pushing, wants the agent to verify the commit actually reached remote and nothing is left unpushed: compare local HEAD vs `origin/main` (ahead/behind counts), confirm the working tree is clean, and confirm the agent's own session files are present in the committed tree (e.g. `git cat-file -e HEAD:<path>`) — not just trust a "committed" claim. Confidence: 0.6
- Thinks of the agent's work in discrete rounds/groups and will ask to explain recent ones ("what were the changes you did recently… the last 2-3 group of changes"); wants the recap organized by group with rationale and any risks/cautions called out explicitly, not a flat diff. Confidence: 0.6
- Feature work follows an explicit gather-context → plan → implement sequence: "gather the complete knowledge about it by reading the code and the appropriate code files … gather the context first and then lets plan it and then implement the same." Context gathering must verify the whole data lifecycle — input/UI → validation → what's actually stored in the DB → whether stored fields are really used in computation → what each page actually displays (real vs hardcoded) — rather than trusting prior descriptions or assumptions. Context gathering should dispatch parallel subagents (explore agents) to investigate different areas of the codebase simultaneously — "create subagents to gather the context first and then start with the plan and the implementation of the same." Confidence: 0.8
- Wants Playwright e2e tests exercising the real user flow as part of delivering a feature ("use playwright e2e test to check the real user flow and make sure everything is working correctly"), e.g. login → home shows real match % → open profile → shortlist, asserting real computed values instead of hardcoded placeholders. Also expects Playwright MCP (browser automation) to be used for interactive post-implementation verification — "also use playwright mcp to check if everything is working out or not." Confidence: 0.75
- Background long-running commands (e.g. Playwright booting the dev stack) can open a new terminal window that shows no output — the user treats this as normal and says to just continue: don't stall or ask what to do, keep polling the original background shell handle until it exits and proceed with the workflow; when a stalled run still shows no output the user asks to kill and restart it fresh — stop the shell, clean up orphaned dev servers still holding the ports, then relaunch. Background shellout logs repeatedly come back empty even after exit, so when output matters (test results, error text) run the command in the foreground with a generous timeout or redirect to a file (`> log 2>&1`) and read that file instead. Confidence: 0.6
- Proactively probes performance and scale implications when reviewing how a feature is built ("how is the performance and latency coz at 1000s of profiles later on it ll be an expensive and time consuming process"): wants an honest current-shape vs. what-breaks-at-scale assessment up front, then picks the pragmatic incremental fix (hard filters pushed into indexed SQL, deterministic ordering, larger bounded pools, short TTL cache) over precompute tables/nightly jobs until volume actually demands them. Confidence: 0.7
- For product/feature design on this matrimonial app, benchmarks against established Indian matrimony platforms — explicitly asks to "refer to other matrimony apps in India like shaadi.com etc" so field sets, enums and flows match industry conventions rather than being invented. Confidence: 0.65
- Explicitly invites clarifying questions when the agent is unsure ("ask clarifying questions on wherever you have doubts") rather than having the agent guess on product/domain decisions; pair the questions with the reference benchmarks and a recommended default. Confidence: 0.6
- On Windows with `core.autocrlf = true`, `git status` can show "modified" for files that have zero real content diff (CRLF stat-cache artifact). When the user independently runs `git status` post-push and pastes unexpected "modified" files, investigate the real diff with `git diff HEAD --name-only` before concluding — show the empty diff as proof and explain the cosmetic flag rather than re-committing or alarming the user. Confidence: 0.6
- Full-stack field batches follow a reusable spec template the user pastes per field group: before coding, fill a pipeline matrix auditing each column across every layer (DB type/null × Zod register × Zod PATCH × service insert/update × payload key × hydrate key × register UI × edit UI × own display × other display × completeness), marking gaps explicitly (orphan DB column, UI-only never persisted, write-only/read-dropped, fabricated defaults, wrong alias, cannot-clear-to-NULL, displayed incorrectly, completeness mismatch). Then implement fixes across all layers in order (DB → types → Zod → API service → web store/payload/hydrate → UI → display → rebuild validation dist → tests), and close with a structured handoff report (final pipeline matrix, gaps found→fixes, where asked/shown, test evidence with commands, follow-ups deferred). This is the concrete field-batch form of the general gather-context→plan→implement preference. Confidence: 0.8
- When a UI section looks confusing or misaligned, shares screenshots (often without describing the problem in text) and expects the agent to inspect them via vision, diagnose the specific UX/layout issues (broken grouping, inconsistent button styles, cramped inputs, misaligned columns, unclear primary action), fix them, and verify with typecheck — all aligned to the project's design tokens spec (`specs/ui-ux.md`: maroon `#7c1535`, gold `#b8901f`, Outfit/Cormorant fonts, pill buttons, `rounded-2xl` cards, 44px tap targets). Consult that spec file before writing any UI changes. Confidence: 0.7
- Onboarding-critical data must be collected inside the registration/onboarding flow itself, not deferred to later profile editing: explicitly asked that partner preferences be "a part of the registration or the onboarding flow itself and not get it later on" — treat required matching inputs as signup-time concerns, and prefer inserting a wizard step over a post-registration nudge page. Confidence: 0.7
- When asking for a feature plan, wants it reasoned as a product manager (the user experience of the flow) AND validated against the existing architecture and business requirements — "think in terms of user experience product manager and also make sure the plan matches our architecture and our business requirements as well". Confidence: 0.75
- Expects the agent to use available specialized skills (e.g. `ui-ux-pro-max`, product-thinking skills) when designing UX/product features — "make sure you use the appropriate skills such as ui ux pro max or other product thinking ones to appropriately design and make sure the functionalities are properly taken cared." Activate and consult these skills before writing UI/UX plans. Confidence: 0.7
- When requesting a feature/revamp plan, wants it structured by layer: separate sections for frontend changes, backend API changes, and testing (unit + integration + e2e) — "split the plan for separate frontend changes and then the backend api connecting to it and then testing part." Confidence: 0.7
- Feature delivery includes a full layered test suite stated up front: explicit unit + integration + e2e tests covering real-life scenarios and edge cases, proven to pass, followed by typecheck AND build gates — "make sure to write the unit integration and e2e tests ... and then make sure they work as intended and tests pass and then check the typecheck and the build passes or not". Tests are expected to catch real bugs (their new suite surfaced inverted-range validation and a seeding race), not just document the happy path. Confidence: 0.8
- Expects the agent to leave git commits alone unless asked and to keep repo state explicit: asked "is this on main branch? or whats happening" and accepted the standing rule of committing only on request — surface current branch and what is committed vs. uncommitted, and never sweep unrelated in-progress files into a commit. Confidence: 0.55
